# 逻辑地址子库数据库视图与字段字典

## 1. 数据访问边界

内部可信下游默认使用独立只读账号访问完整业务数据库：

```text
数据库：由环境交接单提供
可读Schema：dispatch_assist、ai
句柄状态视图：logical_address_scope_summary
通用明细视图：logical_address_scope_item
热词窄字段视图：logical_address_scope_hotword_item
源记录引用视图：logical_address_scope_source_ref_item
唯一查询条件：scope_id
```

账号对`dispatch_assist`和`ai`现有表、视图、序列具有只读权限，可在按`scopeId`取得候选后继续查询真实`ai.aoi_* / ai.poi_* / ai.loi_*`源表补充属性。账号设置`default_transaction_read_only=on`，不能修改任何定位、地址或源数据表。这里的“完整数据库”指当前两个业务schema的完整只读能力，不包含写权限和系统管理权限。

## 2. 为什么查询视图就能知道地址在范围内

`scopeId`先通过主键找到本次电话冻结的`search_area`和`inventory_version`。PostgreSQL随后通过全局地址表的GiST空间索引筛出包围盒可能相交的记录，再使用`ST_Intersects`精确判断几何是否相交。

因此视图返回的每一行都已经满足：

```text
地址有效 = true
地址库存版本 = 句柄绑定版本
地址几何与本次search_area相交
逻辑子库仍在有效期内
```

这不是全表扫描，也不需要下游再次计算坐标或圆形范围。

创建句柄时，定位服务使用相同GiST空间索引执行`EXISTS`判断。数据库找到第一条相交记录就停止：有记录写入`READY`，没有记录写入`EMPTY`，不会为了生成句柄统计全量地址数。

查询句柄状态：

```sql
SELECT scope_status, inventory_version, expires_at
FROM dispatch_assist.logical_address_scope_summary
WHERE scope_id = CAST(:scopeId AS uuid);
```

## 3. 字段字典

| 字段 | PostgreSQL类型 | 可空 | 说明 |
|---|---|---|---|
| `scope_id` | uuid | 否 | 本次逻辑子库句柄 |
| `location_resolution_id` | uuid | 否 | 定位结果ID |
| `location_resolution_version` | integer | 否 | 定位版本 |
| `inventory_version` | varchar(64) | 否 | 全局地址库存版本 |
| `inventory_id` | uuid | 否 | 统一地址读模型主键；稳定游标字段 |
| `source_type` | varchar(16) | 否 | `BUILDING/AOI/POI/LOI` |
| `source_id` | varchar(128) | 否 | 源数据业务标识，通常含源表和源主键 |
| `standard_name` | varchar(512) | 否 | 标准名称 |
| `short_name` | varchar(512) | 是 | 简称 |
| `full_address` | varchar(1024) | 是 | 完整地址文本 |
| `aliases` | jsonb | 否 | 别名数组；默认`[]` |
| `parent_aoi_id` | varchar(128) | 是 | 直接父AOI标识；层级完整性由源数据决定 |
| `aoi_name` | varchar(512) | 是 | 所属AOI名称 |
| `road_name` | varchar(512) | 是 | 所属道路名称 |
| `hit_level` | text | 否 | `HARD_AREA`或`SEARCH_AREA` |
| `longitude` | double precision | 否 | 代表点WGS84经度 |
| `latitude` | double precision | 否 | 代表点WGS84纬度 |
| `source_system` | varchar(64) | 否 | 来源系统 |
| `source_table` | text | 否 | 带Schema的来源表，例如`ai.poi_3` |
| `source_record_id` | text | 否 | 解析后的来源记录主键 |

说明：AOI可能使用面几何，POI常使用点几何。`longitude/latitude`是统一代表点，是否进入逻辑子库以原始`geom`与范围相交为准，而不是只判断代表点。

统一视图只包含AOI、POI、建筑物和道路的公共字段，不是源表整行副本。需要楼层、房间、建筑扩展属性、出入口或AOI多父关系时，使用`source_table + source_record_id`回查`ai`源表，具体映射和SQL见[08-AOI、POI原表回查与字段映射说明](08-AOI-POI原表回查与字段映射说明.md)。

## 4. 基础查询

### 4.1 查看一个逻辑子库的全部类型数量

```sql
SELECT source_type, COUNT(*) AS item_count
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
GROUP BY source_type
ORDER BY source_type;
```

### 4.2 热词加载读取原始地址字段

```sql
SELECT inventory_id,
       source_type,
       standard_name,
       short_name,
       full_address,
       aliases,
       aoi_name,
       road_name
FROM dispatch_assist.logical_address_scope_hotword_item
WHERE scope_id = CAST(:scopeId AS uuid)
ORDER BY inventory_id;
```

该窄字段视图只提供原始地址候选，不包含几何和源表扩展字段，也不承担词面去重、Top-K、权重或ASR装载。确实需要遍历全部地址词面时必须使用JDBC流式读取。

### 4.3 地址机器人读取结构化信息

```sql
SELECT inventory_id,
       source_type,
       source_id,
       standard_name,
       full_address,
       parent_aoi_id,
       aoi_name,
       road_name,
       hit_level,
       longitude,
       latitude,
       source_table,
       source_record_id
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
ORDER BY inventory_id;
```

### 4.4 只取AOI和POI

```sql
SELECT inventory_id, source_type, standard_name, full_address
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
  AND source_type IN ('AOI', 'POI')
ORDER BY inventory_id;
```

## 5. 大结果集读取

### 5.1 稳定游标

第一页：

```sql
SELECT inventory_id, source_type, standard_name, full_address
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
ORDER BY inventory_id
LIMIT 1000;
```

后续页使用上一页最后一个`inventory_id`：

```sql
SELECT inventory_id, source_type, standard_name, full_address
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
  AND inventory_id > CAST(:lastInventoryId AS uuid)
ORDER BY inventory_id
LIMIT 1000;
```

不要使用不断增大的`OFFSET`，否则后续页面越来越慢。

### 5.2 JDBC流式读取要求

PostgreSQL JDBC流式游标应：

1. 使用只读事务；
2. 将连接`autoCommit`设为`false`；
3. 将Statement的`fetchSize`设为500至2000，建议从1000开始；
4. 逐批处理，不把所有地址一次放入List；
5. 完成后及时提交或回滚并释放连接。

## 6. 性能约束

- 每条业务查询必须带等值条件`scope_id = :scopeId`；
- 类型过滤应同时写在同一SQL中；
- 地址机器人应将名称、类型或当前处理条件放进同一SQL，不应先取出全部地址再在内存过滤；
- 热词加载仅在确实需要全量词面时读取`logical_address_scope_hotword_item`，并使用流式游标；
- 禁止从逻辑视图执行无`scope_id`的全局查询；
- 不需要先查询全库ID再在内存过滤；
- 不需要把`search_area`传给下游；
- 连接池大小必须根据实例数和数据库连接上限统一规划，不能每个消费者自行无限放大。

## 7. 生命周期与0条结果

当前逻辑子库默认TTL为86,400秒，可由部署参数修改。视图只返回`ACTIVE`且未过期的句柄数据。

新事件携带`scopeStatus`：

- `READY`：至少存在一条空间命中记录；
- `EMPTY`：句柄有效，但该范围在绑定库存版本中没有地址；
- `UNKNOWN`或字段缺失：迁移前的旧句柄/旧消息，需要查询确认。

`EMPTY`不是系统错误，下游不必查询明细视图即可结束本次处理。若状态为`READY`但查询为0条，应检查TTL、库存版本、数据库环境及权限。句柄不存在或过期时，状态视图无记录；不能直连数据库的下游可调用REST确认，当前实现返回HTTP 400和`INVALID_REQUEST`。

## 8. 权限配置

DBA先创建独立登录角色，再执行项目脚本：

```powershell
psql -v scope_reader_role=hotword_loader_reader `
  -f db/ops/grant_address_scope_reader.sql

psql -v scope_reader_role=address_robot_reader `
  -f db/ops/grant_address_scope_reader.sql
```

脚本会向已有角色授予`dispatch_assist`与`ai`两个schema的全部现有表只读权限，并配置默认权限覆盖后续由定位库所有者新建的表。两个下游不能共用同一账号，便于撤权、审计和限流。密码通过密钥系统下发，文档和MQ消息中不得出现。

## 9. 验证索引是否生效

数据库人员可在测试环境执行：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT inventory_id
FROM dispatch_assist.logical_address_scope_item
WHERE scope_id = CAST(:scopeId AS uuid)
ORDER BY inventory_id
LIMIT 101;
```

执行计划应出现逻辑范围主键访问和`idx_address_inventory_active_geom_gist`，不应对百万地址做全表顺序扫描。生产环境执行`ANALYZE`类语句须遵守DBA变更规范。
